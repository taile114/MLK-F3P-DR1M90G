# 分配复用与 CPU 算子融合验证

本文规定冻结 FKP-DVGT 的融合执行、内存复用及回放对照。融合 FP32 CPU 与两个 NPU 分支的混合实现均完成 184 窗验证；相对同条件原生 CPU 参考，三轮平均耗时比约 4.4。收益来自执行实现优化，未重新训练或更改检查点、样条网格、量化尺度及数据划分。

## 实现与计算边界

| 优化 | 实现与保持条件 |
|---|---|
| 工作区复用 | 初始化时创建各算子的张量缓冲区和执行计划；回放期间不重新构建图、张量形状或输入输出绑定 |
| Reshape 视图 | 连续数据只更改形状视图，不复制或创建新的浮点输出缓冲区；必要的转置和非连续切片仍执行复制 |
| KAN 融合 | 一个 CPU 内核完成 SiLU、左闭右开的门控及三阶样条递推；保留原网格、边界和运算定义，不使用查表近似 |
| KAN 共享 | 30 个独立输入/网格的基函数结果在相应 Q/K/V 分支间复用，保持 124 个线性分支及原模型拓扑 |
| PCC、LayerNorm | 合并均值、中心化、平方和等操作，保留 `1e-8`、`1e-5` 及原定义，减少中间张量 |
| NEON 点积 | 显式 float32 SIMD，关闭浮点乘加收缩，不启用 fast-math；累加次序变化以原 FP32 容差验收，不要求逐位相等 |
| NPU 边界 | 两个回归头样条 FC 保持实数零补齐、UINT8 尺度与偏置；持久 CMA 输入输出通过 import/export 复用，量化、同步和恢复计入前向时间 |

五处 GELU 保持原 `std::erf` 定义，模型输入和输出顺序不变。源码为 [native_rul_fused.cpp](../probe/native_rul_fused.cpp)、[CPU 内核](../probe/fused_ops.hpp)及[量化 FC](../probe/fused_quantized_fc.hpp)。原始实现保留；[参考程序](../probe/native_rul_reference_bench.cpp)使用相同原生图与库，关闭逐段内存日志及 profiling、移出首窗写盘并加入五窗预热。

融合计划含 375 个执行回调和 1011820 字节持久浮点张量工作区；该字节数不含权重、索引表、运行库或进程其他内存，不能解释为总 RAM 占用。旧 CPU 首窗 profile 的非 Constant 事件为 1779 次，该统计不是新实现的稳态热点分布。

## 数值与内存证据

训练集校准参数保持冻结；本轮使用电机 6 的 184 窗验证数据，没有新测试集推理。标量和 NEON 融合 CPU 在交叉环境均完成全验证集；板端融合 NEON 的最大参考差为 `8.106231689e-06`，没有超过原 `0.0001 + 0.0001*abs(reference)` 容差。验证 RMSE 约 2.46594014，原生参考约 2.46593998。

| 配置 | 验证 RMSE | 相对原 FP32 最大偏差 | 计时区间 C++ new 调用/184 窗 |
|---|---:|---:|---:|
| 原生 CPU 参考 | 2.46593998 | 0.00000763 | 3843944 |
| 融合 FP32 CPU | 2.46594014 | 0.00000811 | 0 |
| 融合 CPU 两分支量化 | 2.46570404 | 0.01163197 | 0 |
| 融合 CPU/NPU | 2.46797651 | 0.03055000 | 13312 |

[allocation_probe.hpp](../probe/allocation_probe.hpp)统计计时区间的全局 C++ `new/new[]` 请求，包含被链接库中的相应调用，不是所有 C `malloc`、内核或硬件分配的完整审计。计数仅在前向期间启用，累计申请量不等于峰值或驻留内存。该头文件用于单翻译单元诊断程序，应用接入时应封装或移除全局钩子。

混合回放的 CMA 为 118784 字节，1/10/184 窗及三轮对照均保持稳定。分段 ArmNN 混合参考的 1204224 字节记录保留在 [CMA 对照](rul-quantization-validation.md)。本轮证明固定形状回放的复用与清理，不替代长期运行或反复加载/卸载验收。

样条夹具包含均匀/非均匀网格、精确结点、结点两侧相邻 float32、范围外值和固定随机值，共 105×3 个输入。板端与 PyTorch 导出的基函数及样条最大差为 `2.384185791e-07`。完整验证集同时覆盖实际冻结网格的前向计算。

NPU 在 1/10/184 窗逐步验证，保存实际量化输入、权重、输出及尺度。[独立脚本](../tools/verify_fused_replay.py)从冻结权重重新生成 UINT8 权重，以 int64 矩阵乘法和相同尺度重定标核对共 14040 个物理输出，最大差 1 LSB。另检查实际 ALHardNPU 图、首个测量窗两次 NPU 执行及硬核 IRQ。五窗预热计入 IRQ 快照，184 窗时硬核增量为 567，软核为 0。

量化分支的 `mismatches` 仍表示超过原 FP32 容差的预测数，不是整数计算失败。融合 CPU 量化使用显式整数参考，舍入可能与原厂 CPU 量化核不同；两者不宣称逐位相同。应用精度阈值仍为 TBD。

## 三轮预热回放

每个进程先用验证窗口 0 预热五次，再按同一顺序回放全部 184 窗。四种模式执行三轮交错顺序；编译均为 `-O3 -ffp-contract=off`，使用相同板卡、系统和配套库。初始化、CSV 写出、原始整数审计及结果归档不计入前向时间。NPU 首个测量窗保留 profile 事件，其余窗口不启用 profiling。

| 模式 | 三轮均值 ms/窗 | 各轮均值范围 ms/窗 | 相对原生参考耗时比 |
|---|---:|---:|---:|
| 原生 ArmNN CPU 参考 | 195.328 | 194.829–195.639 | 1.000 |
| 融合 FP32 CPU / NEON | 44.428 | 43.945–45.388 | 4.397 |
| 融合 CPU、两分支量化 | 45.263 | 44.670–46.109 | 4.315 |
| 融合 CPU/NPU、两分支量化 | 44.965 | 44.031–45.433 | 4.344 |

各模式重复回放的预测逐位一致。P50/P95 和逐轮值见[完整复核](../results/board/fused-replay-v1-verification.json)。CPU 频率及温度控制接口未获取，因此该结果为同板交错回放对照，不宣称硬件极限性能或满足尚未定义的应用指标。

两个 NPU 分支没有体现稳定的额外端到端收益，融合 CPU 和混合实现均约 44–45 ms/窗。此次明显加速应归于整个融合与分配复用方案，不能全部归于 NPU，也不能据此断言 DDR 带宽已经饱和。后续热点应针对融合后的实现重新分析。

额外分支的独立测量见[后续验证](additional-offload-validation.md)：四个前馈样条 FC 及输入投影的等价卷积已完成完整验证回放，保留单层收益、预测偏差及整模型耗时的分别对照。

## 部署与复核

[冻结包](../artifacts/f3p-fused-rul-arm64-v1.tar.gz)含程序、源码、样条夹具、184 窗验证数据、超时工具和 26 项内部校验；提供原生 CPU 包中相同的 `weights.bin/weights.tsv` 后，核对 `weights.sha256`。包内 `benchmark.sh` 自动使用自身目录，实机记录中的驱动使用明确的 SD 目录，试验顺序相同。

在新的 Linux 解压目录执行，每组核对成功后再继续：

```sh
sha256sum -c checksums.sha256
sha256sum -c weights.sha256
sh run.sh stem
sh run.sh neon 1
sh run.sh neon 0
sh run.sh hybrid 1
sh run.sh hybrid 10
sh run.sh hybrid 0
sh benchmark.sh
```

上述命令读取本地数据，不使用 U 盘；U 盘部署的挂载规程见[测试说明](testing.md)。[构建脚本](../probe/build_native_fused.sh)使用配套 CXX、ARMNN_ROOT，CPU 与 NPU 初始化完成后再计时。[原始文件哈希](../results/board/fused-replay-v1-files-sha256.json)覆盖 457 个回收文件，电脑只读复核入口为 `python tools/verify_fused_replay.py`，不执行推理。

串口回收按 64 KiB 分块、核对完整 SHA-256。内核 USB 日志可能插入控制台数据流，因此仅在下载块内临时降低控制台日志级别，退出时恢复；内核环形日志保留，恢复值和传输证据见[返回记录](../results/board/fused-replay-v1-return.json)。

## 后续范围

1. 定义预测周期及允许精度退化；冻结方案后再执行独立测试集验收。
2. 对候选实现做长时间运行及重复加载/卸载压力测试，应用接入时保留 CMA 清理顺序。
3. 将融合执行计划封装到项目推理接口；当前为固定模型的独立回放程序。
4. 若需要继续提高速度，重新分析融合后的热点，评估额外 NPU 分支或更大的连续分段，保留真实层、精度和端到端收益的逐级验收。
