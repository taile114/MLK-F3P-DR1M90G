# 文档与报告写作约定

> 适用于本仓库的技术文档、README、报告与提交说明。目标是让各方向成员（PS、PL、NPU、EDA 等）与 agent 都能直接阅读和修改，并保持仓库文档一致。

## 1. 语气

- 中立、客观、陈述式，对事不对人。
- 不把读者预设成某个方向或身份：不用「你 / 你们 / 队友」；范围句描述内容，不写「给……看的」这类限定。
- 不以「用户 / 我们 / 作者」作主语叙述过程；需要说明来源时写来源（如厂商手册、设计评审、实测）。
- 不写交差、免责、抱怨式语句，例如「本仓库不代建 PL 端」「我们不负责……」。
- 不写教学 / FAQ 语气，例如「先回答……」「别搞错」「记住」「怎么办」，也不用「为什么……」作小节标题。
- 不用口语、感叹、拟人，例如「坑 / 踩坑 / 搞定 / 打嗝 / 焊死 / 随便 / 盲打 / 会崩 / 最快 / 给不了 / 双赢 / 血流成河」等。

## 2. 符号与状态

- 不用 emoji 或状态符号：`⚠️`、`✅`、`❌`、`⛔`、`✓`、`✗`、`★`、`ℹ️`、`📊` 等一律不用。
- 结论与状态用词表达：`可用`、`受限`、`不可用`、`已修`、`已解决`、`待定`。
- 契约 / 规格中的未定值用固定标记：`TBD`（待定）、`REF`（参考值，待实测确认）、`OK`（已冻结）；不用 `☐`、`△`、`☑`。
- 强调靠措辞和表格，不靠大量加粗与感叹。

## 3. 内容

- 交代清楚三件事：是什么、为什么、怎么做。
- 只写与仓库事实一致的内容：路径、文件名、命令、器件名、网络名、位号要与实际一致。
- 不确定的内容标 `TBD` 或注明来源；不写推测。
- 路径写成相对本文文件的正确路径；引用仓库内文件用 Markdown 链接。
- 术语统一：PS / PL、TD、FD、Buildroot、TD 工程等沿用仓库既有写法。
- 必要的限定与来源写进正文或引用，不堆砌无意义的括号解释。

## 4. 不写历史

- 不写自更正与文档整理过程，例如「更正：旧版本写……」「曾误写……已改」「原文档已删除 / 已并入本文件」「旧口径不再维护」。
- 不写带日期的变更 / 修复 / 审计记录（`2026-xx-xx`、`t8`、`变更史` 等）；器件、电路、接口、软件一律以当前事实为准，改动后直接更新正文。
- 只保留当前结论与事实。

## 5. 结构与面向对象

- 长文档开头用一句话说明范围，描述内容而非限定读者身份。
- 命令用代码块；路径与标识符用反引号；步骤按实际执行顺序排列。
- 接口契约、开发流程、规格这类主要由 agent 阅读和修改、由人检阅的文档，用规格 / 规程样式，不用报告体：
  - **接口契约**：地址、寄存器、位域、复位值、中断、DMA、时序等逐项列全，字段级表格；写清单一权威来源，以及「谁能改、怎么改、何时升版本」的规则。
  - **开发流程**：前提、步骤（操作 / 命令·路径 / 产物）、交接物、构建与烧录按执行顺序排列。
  - **状态表**：状态用词统一（见 §2），不用符号。

## 6. 用词对照

| 不写 | 写 |
|---|---|
| `⚠️` 注意 / `✅` 可用 / `❌` 不可用 | `注意：` / `可用` / `不可用` |
| 别把…… / 绝不能 / 别用 | 不得…… / 不…… |
| 坑、踩坑 | 问题、缺陷 |
| 打嗝 | 间歇脉冲 |
| 焊死 | 固定 |
| 随便插 | 可自由插拔 |
| 得 WiFi | 提供 WiFi |
| 会崩 | 将导致异常 |
| 最快 | 快捷方式 |
| 一定要限流 | 限流（必须） |
| 谁不能挨着谁 | 不能相邻的器件 |
| 为什么换 X | 换 X 的原因 |
| 更正：旧版本写…… | （删除） |

## 7. 例子

不合适：

> 本文给「你（PS 端）」和「队友（PL 端）」……本仓库不代建 PL 端代码。

合适：

> 本文描述 PS 与 PL 两条线的步骤与接口。PL 代码位于 `fpga/`，PS 代码位于其各自位置。

不合适：

> `OC_FLAG` 是"打嗝"不是锁存。⚠️ 触发后该腿会被锁存关断。

合适：

> `OC_FLAG` 触发后表现为间歇脉冲（PWM 恒低 → 电流缓降 → 释放），不是电平锁存。
