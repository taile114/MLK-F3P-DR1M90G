# 寿命模型与上位机接入

本文规定冻结 FKP-DVGT 的数据集回放、板端推理、HDMI 显示、PC 控制与结果记录。真实采集适配另行验收。

## 1. 运行结构

`板端已归一化输入 → ReplayWorker → npu_* → libmlk_rul.so → ReplayController → HDMI / UDP v3 / 寿命记录`

Qt 主线程负责采集、显示和网络；独立 QThread 负责模型校验、初始化、五次预热、单窗推理、结果记录及释放。只允许一个模型实例和一个待执行的推理任务。图、权重与工作区在初始化时创建，推理时复用；不读取标签或参考预测。

| 项目 | 定义 |
|---|---|
| 模型 | `motor_stable23_v1`，完整冻结 FKP-DVGT |
| 输入 | little-endian float32 `[1,23,110]`，2530 个值 / 10120 字节 |
| 输入来源 | `val184` 或 `test165` 数据集的已归一化窗口，不重复归一化 |
| 输出 | float32 RUL，单位 `observed_aging_test_session`（剩余观测老化试验轮次） |
| 分类 / 分级 / 置信度 | 不可用，不从 RUL 或传感器阈值推导模型分类 |
| CPU | 融合 FP32 / NEON |
| CPU/NPU | 融合 CPU + FF6 六个指定样条 FC 的 UINT8 硬核执行；其余计算在 CPU |
| 默认回放间隔 | 每次结果返回后等待 1000 ms；可设 100～60000 ms，不表示观测采集周期 |
| 时间 | `infer_us` 仅计单窗前向；加载、预热、输入读取、记录及网络传输不计入 |

模型输入的 10 次观测不等于连续十秒。训练通道为三相电流、三相电压、两个加速度、麦克风、转速、温度；现场温度与三轴振动不能直接填入该输入。来源与预处理见 [模型说明](../npu/docs/model-and-data.md)。

选定部署目标为 `ff6`（四个前馈首层样条 FC + 两个原回归头样条 FC），独立程序三轮 184 窗均值为 43.358 ms/窗，最大 FP32 预测差约 0.048573 轮。应用封装支持同一六分支计划，源码生成、身份校验和构建流程见[运行包 README](../host/ps-local/inference/README.md)。应用共享库已完成 QEMU CPU 与板端 CPU / FF6 各两轮 184 窗核对，FF6 与冻结独立程序逐窗结果一致；本地 HDMI 回放可用。应用共享库的独立验证见[应用验证摘要](../host/tests/results/ff6/summary.json)。合并镜像已完成两轮 184 窗混合回放及 HDMI / 采集 DMA 基础共存核对，见[合并镜像摘要](../npu/results/board/combined-soc-ff6-hybrid.json)；长期稳定性另行验收。

## 2. 构建模型运行包

Windows 或 Linux 在仓库根执行，输出目录须不存在：

```sh
python host/ps-local/inference/prepare_runtime.py --output /absolute/new/runtime
```

工具核对冻结归档 SHA-256，提取原生权重、融合执行源码、模型配置、六个分支的冻结校准参数及 184 窗输入。生成应用接口时移除回放 CLI、全局 C++ 分配钩子及正常路径的诊断写盘，不改动 `npu/` 原件。原始诊断程序和证据保持独立。

在配套 Ubuntu 开发环境中设置工具链与 ArmNN 头文件 / 库根目录后执行：

```sh
export CXX=/home/uisrc/uisrc-lab-anlogic/tools/aarch64-linux/bin/aarch64-linux-gnu-g++
export ARMNN_ROOT=/home/uisrc/f3p-rul-probe/vendor/armnn
sh /absolute/new/runtime/build.sh
```

生成 `libmlk_rul.so` 与独立检查程序 `check_engine`。Qt 应用通过 C ABI v1 动态加载共享库，不需要在 Qt 构建时包含 ArmNN 头文件。运行库仍须与厂商版本配套。

编译后回到仓库环境封装校验清单：

```sh
python host/ps-local/inference/prepare_runtime.py --output /absolute/new/runtime --seal
```

`model.json` 固定 `execution_plan=ff6`、`quantization_plan=qparams_ff6.tsv`、`npu_branches=6`、输入形状、特征版本、归一化状态、单位和数据集标识，并保存权重、索引、校准、输入、共享库的 SHA-256。应用加载前逐项检查；缺失或不匹配时显示不可用，不生成替代预测。

## 3. 部署与环境

| 路径 | 内容 |
|---|---|
| `/opt/qt_play/` | `mlk_ps_local`、Qt 运行库、启动脚本 |
| `/opt/mlk_rul/` | 已封装的模型运行包；不要求部署参考预测或标签。可选放 `labels_f32.bin`（float32 小端，元素数等于窗口数）或 `labels.csv`（`sample_index,rul_cycles`），面板据此在寿命预测后显示该窗口的预测偏差；文件缺失或长度不符时不显示偏差 |
| `/opt/armnn_lib/lib/` | 配套厂商运行库与依赖 |
| `/dev/hard_npu`、`/dev/cma_mem`、`/dev/soft_npu` | 混合后端所需设备；合并 `soc_hdmi` 工程含厂商 `Video_NPU`，须同时使用配对设备树与内核；合并镜像基础共存可用，长期稳定性待定 |
| `/dev/fb0` | HDMI 本地显示 |
| `/dev/pl_ctrl` | 现场采集；其缺失不妨碍数据集回放 |

模型目录可在本地回放面板编辑并保存到 QSettings；修改前先停止回放。启动时环境变量 `MLK_RUL_ROOT` 优先于保存值。远端控制仅操作该已配置目录，不能下发任意模型路径或代码。

`platform/flash/stage_rul.sh` 通过 `RUL_BUNDLE`、`ARMNN_RUNTIME_ROOT` 将运行包和配套库加入 rootfs overlay；`stage_ps_local.sh` 在设置 `RUL_BUNDLE` 时调用该步骤。该步骤不证明内核、设备树和码流已经满足 NPU 与 HDMI / 采集共存条件。

使用 [只读环境检查脚本](../host/ps-local/inference/inspect_environment.sh) 核对设备及运行库。采集与 NPU 同时启用前，须核对以下项目：

1. 板上 PL ID 为 `0x504C0102`（v1.2），匹配当前 PS 代码的寄存器窗口与 DMA 字格式。
2. HDMI / 传感器 AXI、驱动、DTB 与实际码流匹配。
3. 传感器 DMA 的 `0x3EF00000` / 1 MiB `no-map` 区域与 NPU CMA、U-Boot 常驻区无重叠。
4. 硬核 NPU 驱动、时钟、复位与中断在候选系统可用；码流没有实现的软核 NPU 不能作为可用加速资源。
5. 同时运行 HDMI、采集与混合推理时，资源释放、DMA 丢块及系统稳定性通过实板验收。

手动选择的后端在初始化或推理失败时显示错误，不自动切换。数据集回放不随开机自动启动：本地面板的「开始/继续」或远端回放指令才发起调度，后端由用户选择（`CPU/NPU` 需要 `/dev/hard_npu`、`/dev/soft_npu` 与 `/dev/cma_mem`），界面始终显示实际后端。正常停止等待正在执行的调用结束后释放模型；厂商驱动若不返回，线程无法强制中断该内核调用，服务最终超时行为仍以 `S99qtapp` 为准。

## 4. 操作与状态

| 操作 | 行为 |
|---|---|
| 开始 / 继续 | 已停止时从窗口 0 重新开始；暂停中未改窗口编号时执行下一窗，改动后从该编号开始；未加载时校验并初始化 |
| 暂停 | 不再提交下一次推理；正在执行的窗口允许完成，窗口编号保持当前值可编辑 |
| 单步 | 从窗口编号执行一个窗口，返回后暂停 |
| 停止 | 清除结果有效标志，完成当前调用后释放图 / 运行时 / CMA；窗口编号归零 |

界面提供开始 / 继续、暂停、单步、停止四个按钮。协议层保留 action 5 定位与 6 查询，供其他客户端回读状态，界面不再提供对应按钮。

加载、运行、暂停、完成、停止中、已停止、错误分别显示。现场采集持续独立运行，回放结果不归属于同屏现场曲线。模型不支持现有四值模拟注入。

PC 启动监听后，通过配置中的 PS 目标地址 / 端口发送命令；PS 监听本地配置端口。应用帧复用既有安全数据报封装。启用 PSK / ECDH 时拒绝明文应用帧。每条控制命令有请求号、确认及最多四次发送；PS 缓存最近 64 条请求号以避免重试重复执行。命令超时须回读状态，不等同于板端未执行。

PS 每秒发送状态；PC 超过 3.5 秒未收到 v3 状态时显示链路不可用并清除显示结果的有效标志。端口配置改变后重新确认链路。

## 5. UDP v3

所有数值为小端，float 为 IEEE754 float32。magic、seq、ts_us 与 v2 相同；v3 只定义 `type=1` 结果 / 状态及 `type=3` 控制。v1/v2 波形、诊断和注入解析保留；未知版本拒绝。v2 RUL 的单位仍未定义，界面不再默认显示小时。

### 5.1 结果 / 状态（固定 224 字节）

| 偏移 | 字节 | 字段 | 定义 |
|---|---:|---|---|
| 0 | 2 | magic | `0x4B4D` |
| 2 / 3 | 1 / 1 | ver / type | `3` / `1` |
| 4 | 4 | seq | 状态序号，32 位回绕 |
| 8～15 | 8 | 保留 | 0 |
| 16 | 8 | ts_us | 最近有效预测完成的系统时间；状态心跳不刷新该时间 |
| 24 | 1 | task | `1` = RUL |
| 25 | 1 | valid | bit0 = RUL 有效，其余保留 |
| 26 | 1 | source | `1` = 数据集回放 |
| 27 | 1 | backend | `0` 不可用、`1` 融合 CPU、`2` CPU/NPU |
| 28 | 4 | rul | float32，不转为整数、不换算小时 |
| 32 | 4 | infer_us | 完整单窗前向耗时 |
| 36 / 40 | 4 / 4 | window / count | 输入窗口索引 / 数据集窗口数 |
| 44 | 1 | state | 0 停止、1 加载、2 就绪、3 运行、4 暂停、5 完成、6 错误、7 停止中 |
| 45 | 1 | unit | `1` = observed_aging_test_session |
| 46 | 2 | command_status | 0 普通状态、1 命令接受、2 命令拒绝 |
| 48 | 32 | model | NUL 结尾 ASCII 模型标识 |
| 80 | 12 | dataset | NUL 结尾 ASCII 数据集标识 |
| 92 | 4 | request_id | 确认的命令序号；普通状态为 0 |
| 96 | 128 | message | NUL 结尾 UTF-8 状态 / 错误说明 |

有效 RUL 必须有限、窗口索引在范围内且后端已知；无有效结果时只显示状态。该协议不定义分类、置信度或分级字段。

### 5.2 控制（固定 40 字节）

| 偏移 | 字节 | 字段 | 定义 |
|---|---:|---|---|
| 0～23 | 24 | 公共头 | magic、ver=3、type=3；seq 为非零 request_id |
| 24 | 1 | action | 1 开始、2 暂停、3 单步、4 停止、5 定位、6 查询 |
| 25 | 1 | backend | 1 CPU、2 CPU/NPU |
| 26 | 2 | 保留 | 0 |
| 28 | 4 | window | 未加载时的起始窗口或定位目标 |
| 32 | 4 | interval_ms | 100～60000 |
| 36 | 4 | 保留 | 0 |

## 6. 结果记录与验收

HDMI 与 PC 将有效结果写入配置记录目录下的 `rul/rul_*.mlkr`，保留完整 v3 帧，包括浮点值、单位、模型、后端、来源、窗口和结果时间。不触发分类故障计数或将现场波形标为模型故障。

每个记录的头部为 `MLKR`、版本 1、加密标志、16 字节盐与 12 字节 nonce；载荷为 v3 帧。启用本地加密时使用 PBKDF2-HMAC-SHA256（100000 次）及 AES-256-GCM，头部为 AAD；每条记录使用新 nonce。禁止加密失败时退回明文。记录按保留月数、最低剩余空间及 10000 个文件上限清理，仅处理寿命记录目录。

寿命记录索引按数值修改时间排序并增量维护，每次写入前检查已索引记录的到期状态、数量和磁盘余量。首次使用、切换目录或目录重建时扫描，正常运行每 30 s 核对一次外部文件变化；自身写入实时更新索引并保持 10000 个文件上限。到期计算使用 UTC 日历月。目录扫描不使用 Qt 按本地修改时间反复比较的排序路径，避免历史文件增多后阻塞同一事件循环的实时接收。

验收顺序：

板端 `ROOT` 取 `/opt/mlk_rul-validation`：该目录放检查程序与参考序列，模型载荷由相对软链指向 `/opt/mlk_rul`，其中 `weights.bin` 与 `weights.tsv` 必须一并可见，否则 `mlk_rul_create` 以 `No weights loaded` 失败。

1. 使用 `check_engine ROOT cpu 2` 对 184 窗做两轮加载 / 推理 / 释放，CPU 容差为 `1e-4 + 1e-4*abs(reference)`。
2. 使用 `check_engine ROOT hybrid 2` 检查重复加载、有限输出、硬核分配、中断和 CMA；混合误差单独报告，应用允许退化阈值为 TBD。
3. 运行 `host/tests/rul.pro` 的协议、输入校验、状态切换、记录认证和安全通道测试；测试替身不进入运行包。
4. 检查 HDMI 与 PC 的结果、单位、窗口一致性，命令重试与链路中断状态。
5. 在匹配的系统 / DTB / 码流上同时运行采集、HDMI 与推理，进行长时间资源、DMA 丢块和优雅停止测试。
6. 方案冻结后独立执行 165 窗测试集验收；真实采集模型的通道、采样率、特征公式、归一化及训练分布单独冻结。
